# 色板生成算法

本工具把配色任务拆成三个问题：根据已有分布逐色寻找同风格的近邻配色、检查实际色码是否满足约束、整理已有颜色的呈现顺序。编辑与首次随机取色允许保留暂时不满足全部规则的起点，审计会如实显示；后续生长和保留固定颜色的替换必须通过当前规则。排序只改变呈现顺序。

当前工作台使用 v3 逐色生长：已有颜色分离较远时补足中间过渡，局部已经紧密时探索邻近色系，使整套颜色形成少量可解释、可连接的群组。目标是两套示例体现的分布结构，不是复制它们的 HEX，也不机械地把“当前最大距离减去最小色差”作为下一步距离。色差下限防止重叠，不能被当成越大越好的风格目标。

v3 复用原有 OKLab / OKLCh 转换、WCAG 比值、八位量化和硬约束检查。`generatePalette` 的 v2 候选池、三轮近邻评分及 `regenerateSelected` 底层 API 继续保留；它们的算法细节和历史实验在本文中单独标明。两套原色表的分布依据见 [配色分析](PALETTE_STUDY.md)，历史 maximin 与 v2 近邻输出保留在第 7 节，不能当作当前 v3 的实验成绩。

## 工作台、示例与计算的边界

工作台每次从 `colors = []` 开始，只维护一份 0–25 色的当前色板。末尾的虚线加号卡与普通色块尺寸一致，点击运行一次新增流程，满 25 色后不再显示；指定 HEX 在左侧编辑器输入，不另设主色列表或新增输入条。生成保留全部现存颜色，沿相同取点流程依次补到 25 色。随机替换保持当前数量：部分选择时保留未选颜色并填回原槽位，全选时从空根重开风格。没有浏览器自动暂存或恢复，也没有从示例原色表采样的分支。

`src/project.ts` 管理可序列化数据：`createProject` 创建空工作台，`effectiveDomain` 解析随当前色板更新 / 固定的范围，`snapshotProject` 为计算与导出克隆完整状态并记录实际有效域。`Project` 不含独立的主色列表；`colors` 保存显示顺序，`growth` 保存颜色的生成关系，两者分别维护。JSON、SVG、PNG 均可导出 1–25 色，名称在保存对话框中填写，色板内不设名称输入行。界面和状态层均不再保留参考方案、JSON 导入或保存参考的逻辑，JSON 仅作为导出格式。

`makeExample` 提供固定水雾森林、暮山陶土的独立副本，供只读预览。`ExampleProject` 额外保留 `anchors` 表示示例的代表色，不是工作台的第二份颜色状态。点击顶部风格按钮只打开原色板与分布，不修改工作台；预览头部关闭按钮左侧的“使用主色”才把代表色载入 `project.colors`，并应用生成域及底色规则，保留当前文字色和最低文字对比。完整 25 原色不会成为工作台生成结果。原色卡点击只负责查看与两图联动，独立加号才逐个取色，不导入示例规则；满 25 色只禁用加号，不禁用查看。

界面由 React 组件管理，顶部是全局规则，左侧只负责当前颜色的分析与编辑，右侧管理色板。已选数量、全选、清空、删除、排序、随机与生成集中在色板标题栏，按用途分组。高级选项始终展开，最低文字对比使用滑杆，1.65 与 4.5 是可点击刻度。编辑对象与选中集合是独立状态：点击色块切换选择，Shift 连选；点击色码只改变编辑对象。“清空”只取消选择，红色“删除”才移除选中颜色；“随机”替换选中颜色，“生成”保留当前全部颜色补到 25 色。数字输入保留本地编辑草稿，在失焦或 Enter 时校验和提交，避免组件更新打断输入。

当前色板的“颜色之间的衔接”直接展开 a/b 与 h/L 分布图、颜色详情、近邻 / MST 与全对统计、约束极值和生成规则边界，不另设“查看空间分布”按钮或当前色板弹窗；固定示例保留原色板预览。`PaletteAnalysis` 将工作台选中集合与编辑下标传给 `distribution-view`：两图同步标记全部选中颜色，当前编辑对象决定常驻详情，悬停或键盘聚焦提供临时预览，图上点击或按 Enter / 空格只定位编辑对象，不改变多选集合。排序、删除沿用工作台的下标映射，因此同一颜色的标记和详情一起更新。此交互不修改颜色或生成算法。空色板不挂载分析；单色仍显示坐标与当前文字色的对比，最近邻、MST 和全对统计显示“—”。

工作台操作由 Web Worker 执行，界面处理取消及结果应用；失败、部分结果或取消不会覆盖当前色板。完整生成成功后自动整理显示顺序，部分随机替换则保留未选颜色的槽位。已有色板与排序结果一致时，排序按钮显示灰色对号和“已排序”；排序保持选中颜色、编辑对象的对应关系，不改变出生顺序和生成父子关系。排序和补点是不同步骤，不把排序状态当作通过约束审计的证明。

应用以 npm 管理依赖，Vite 提供开发与构建入口；安装后通过 `npm run dev` 启动。右上角仅保留“文档”入口，指向 `docs/index.html`，从目录阅读使用指南、算法、配色分析、来源及验证记录。

## 1. 数据与接口

内部使用 OKLab 进行距离计算，使用 OKLCh 表达搜索域，输出不透明的八位 sRGB `#RRGGBB`。OKLCh 的 L 是感知明度、C 是彩度、h 是角度；L 与 WCAG 相对亮度 Y 是不同量，不能直接互换。[OKLab 原始说明](https://bottosson.github.io/posts/oklab/)

```ts
interface ConstraintConfig {
  minDeltaE: number;
  maxBackgroundContrast: number;
  textColor: string;
  minTextContrast: number;
  minChroma?: number; // 工作台默认 0.03；旧 API 未提供时按 0 兼容
  maxChroma: number;
}

interface ColorDomain {
  lightness: [number, number];
  chroma: [number, number];
  hue: [number, number];
}

interface GenerateOptions {
  anchors: string[];
  constraints: ConstraintConfig;
  domain: ColorDomain;
  seed: string | number;
  targetCount?: number;
  sampleCount?: number;
  styleAnchors?: string[]; // 可选软评分参考；全量默认 anchors，局部默认原完整色板
}
```

上述 `GenerateOptions` 是保留的 v2 底层接口。`generatePalette(options)` 返回状态、色码、完整审计、诊断信息、种子和搜索统计；`regenerateSelected(colors, indices, options)` 以未选位置为固定集合，替换选中位置。这两个 API 及历史验证保留，当前界面的新增、补全和随机替换改由 v3 `runPaletteOperation` 统一处理。`sortPalette(colors)` 仅返回重排结果。

主要审计字段包括 `valid`、`issues`、`recommendations`、`minDeltaE`、`closestPair`、`maxBackgroundContrast`、`backgroundExtremes`、`minTextContrast`、`textContrasts` 和 `maxChroma`。其中色差和文字对比在没有可比较对象时可以为 `null`；界面的小数格式只用于显示。

## 2. 三类硬约束

### 2.1 所有颜色对的最小距离

对最终色码转换得到的 OKLab 坐标 `pᵢ = (Lᵢ, aᵢ, bᵢ)`，定义：

```text
D(i,j) = 100 × sqrt((Lᵢ − Lⱼ)² + (aᵢ − aⱼ)² + (bᵢ − bⱼ)²)
minDeltaE_actual = min D(i,j),  i < j
minDeltaE_actual ≥ constraints.minDeltaE
```

这是普通 ΔEOK 的 100 倍缩放。[W3C CSS Color 4，第 20.3 节](https://www.w3.org/TR/css-color-4/)

25 色检查 `25 × 24 / 2 = 300` 对。相邻色差只描述当前排列的步长；即使相邻两色都相距很远，首尾或其他非相邻位置仍可能接近，因此不能用排序后的 24 个相邻距离代替全对下界。

这个下界避免数学意义上过密的色点，但不是“所有课程都能凭颜色辨认”的保证。使用时仍应保留课程名称等信息；色差数值也不能直接按 CIEDE2000 的经验阈值解释。

### 2.2 课程底色之间的最大对比

将最终 sRGB 通道值 `s = channel / 255` 线性化后计算相对亮度：

```text
f(s) = s / 12.92                         s ≤ 0.04045
       ((s + 0.055) / 1.055)^2.4         s > 0.04045
Y = 0.2126 × f(R) + 0.7152 × f(G) + 0.0722 × f(B)
CR(i,j) = (max(Yᵢ,Yⱼ) + 0.05) / (min(Yᵢ,Yⱼ) + 0.05)
```

采用 [WCAG 2.2 的相对亮度](https://www.w3.org/TR/WCAG22/#dfn-relative-luminance) 与 [对比度定义](https://www.w3.org/TR/WCAG22/#dfn-contrast-ratio)。

由于比值随亮端增大、随暗端减小，全套最大值恰好是：

```text
maxBackgroundContrast_actual = (max Y + 0.05) / (min Y + 0.05)
maxBackgroundContrast_actual ≤ constraints.maxBackgroundContrast
```

数学上可由亮度最小与最大的两个颜色精确得到全套最大比值。本版完整审计仍遍历全部颜色对，记录取得最大值的一对颜色。这个参数限制色板的深浅跨度，与文字可读性是独立条件；它不等于 WCAG 的正文对比度要求。

### 2.3 文字颜色与每一种底色

设固定文字色为 t：

```text
minTextContrast_actual = min CR(t,i)
minTextContrast_actual ≥ constraints.minTextContrast
```

引擎不会四舍五入后再判定，也不会自动为某个色块切换文字色。默认白字阈值 `1.65` 是浅色参考范围，**不是 AA 常规正文标准**。常规正文 AA 的阈值为 `4.5`，大号文字为 `3`；还应检查实际使用条件。[W3C Contrast (Minimum) 说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

对纯白字，阈值 r 可化为 `Y底 ≤ 1.05/r − 0.05`。当 r 为 `4.5` 时，Y 必须不大于约 `0.183333`，所以原有水雾浅色会被排除。这属于条件冲突，增加搜索次数无法让同一种浅色通过白字 4.5。

## 3. 搜索域、彩度与八位量化

黑白灰对应中性轴；当前 OKLab 截面中 `C = sqrt(a²+b²)` 是到该轴的径向距离。工作台默认硬区间为 `0.03 ≤ C ≤ 0.11`，用于同时排除过灰和过鲜艳的颜色，首色同样适用。检查针对最终 HEX 重算的 C，手动编辑仍可探索区间外颜色，但审计会明确标出冲突。旧 API 未提供 `minChroma` 时按 0 兼容；上下界必须有限、处于 `[0,0.4]` 且不得倒置。这个默认区间是参考两套原例后选择的工程参数，不是色彩标准定义的审美阈值。

搜索域是 OKLCh 的三维范围，不是现有颜色的凸包。L、C 使用闭区间；h 使用递增圆弧，例如 `[330,45]` 表示跨 0° 的 75° 圆弧，`[0,360]` 表示完整圆周。候选同时受域中的彩度区间与独立 `[minChroma,maxChroma]` 硬区间约束。

工作台初始 `domainMode = 'auto'`，v3 用 `initialStyle` 建立可持续生长的范围，仍复用 `deriveDomainFromAnchors` 处理极值和圆形色相弧。单色的明度余量为 `0.12`，多色为 `0.04`；彩度余量为 `0.025`，色相余量为 `12°`。L 裁到 `[0,1]`、C 裁到 `[0,0.4]`，在生成时与独立 `[minChroma,maxChroma]` 取交集。如果只有一色，或有彩度颜色的覆盖弧小于 `45°`，色相范围改为中心两侧各 `47°`，参考方向取中心及两侧 `35°`；否则沿参考路径展开色相，以路径节点色相的 P20 / P50 / P80 作为三个方向，避免少数端点色主导群组比例。中性灰不以不稳定的色相确定方向，而由种子提供方向。三个方向用于探索评分，不承诺输出恰好三个可分离色簇。

自动范围保存在 `growth.styleDomain`，同一次生长中每加入一个生成色都保持该范围，避免连续点击加号时逐步扩域，使相同输入下逐次新增与一次补全共用同一序列。手动加入、编辑或删除颜色后，根据保留集合重建范围和参考方向；仅改变显示排序不会重建。空色板的有效范围为 L `[0,1]`、C `[minChroma,maxChroma]`、h `[0,360]`。界面不提供“自动拟合”模式选择：直接编辑任何 L、h、C 边界时，先快照全部当前有效边界，再转为 `domainMode = 'manual'`；重置范围恢复生长范围。范围变化不修改色差、文字对比或独立彩度上下界。

全选“随机”会清除旧生长关系并恢复 `domainMode = 'auto'`，新首色建立新的范围；原有全局硬规则保留。部分随机替换冻结操作开始时的有效范围与参考方向，只替换选中槽位。普通新增、补全继续遵守当前自动范围或显式固定范围。首色抽样有意不使用旧自定义域的 L / C / h 与文字对比筛选，但始终满足全局硬彩度区间，规则冲突仍如实审计；后续取点前必须先通过固定集合检查。

`deriveDomainFromAnchors` 的无参数调用仍保留较窄的历史余量：L `0.015`、C `0.02`、h `5°`。`DEFAULT_DOMAIN` 是为水雾森林固定示例及历史实验保留的常量，并非空工作台的默认域。第 7 节的证据使用这组固定输入，不能与工作台自动探索域的输出混为一谈。

候选处理顺序为：

```text
OKLCh 点 → OKLab → 线性 sRGB → 检查色域 → 四舍五入成 HEX
         → 从 HEX 重算 OKLab / OKLCh / Y
         → 检查域、彩度、文字对比、重复与颜色对
```

超出 sRGB 的点直接拒绝，不用通道裁剪把它强行拉入色域。转换允许 `2e-7` 的线性通道误差以覆盖矩阵运算舍入；域与约束判断使用 `1e-10` 的浮点边界容差。这些容差不是放宽一个八位通道的颜色差异。

量化后复核必不可少：浮点候选可能落在允许域内，舍入的 HEX 却跨过域边界、对比阈值或距离下界；两个不同候选也可能变成同一个色码。所有公开指标针对实际输出的 HEX，输出不能依靠量化前的数据通过审计。

## 4. 生成与失败处理

### 4.1 v3 工作台的统一操作与生成关系

`runPaletteOperation(project, operation)` 克隆输入后执行 `growPalette`。操作为 `{ kind: 'add' }`、`{ kind: 'complete' }`，或 `{ kind: 'randomize', indices: [...] }`：

- **新增**：在现存集合后运行一步，数量增加一，最多 25 色。
- **补全**：保留现存 HEX，反复运行同一步，直到 25 色；空色板也可从首色开始尝试。
- **部分随机替换**：未选颜色固定，冻结当前有效范围与风格参考，依次产生与旧色板 HEX 不重复的替换色，放回选中原槽位，数量不变。
- **全选随机替换**：包括只选中唯一一色，从空生长关系开始，恢复自动范围，依次抽取到原数量。保留全部全局硬规则，排除旧色板 HEX；旧色相范围不限制新的起点。

`GrowthResult` 在既有结果字段外返回 `growth` 和 `changedIndices`；全选重开时还返回自动范围状态。`Project.growth` 中的节点记录 `id`、`hex`、`birthOrder`、`parentId`、`strategy`（固定输入、首色、过渡或探索）、与父节点的实际色差和参考方向编号。状态还保存下一出生序号、风格范围、三个方向与初始参考颜色。手动颜色作为固定节点接入；已删除父节点的引用会清除。排序只置换 `colors`，不会重写节点出生顺序；匹配重复 HEX 时使用队列，避免把相同色码的记录混到一起。

同一算法版本中，相同颜色、生成关系、范围、规则与种子确定相同后续序列；逐步种子取 `seed + step + nextOrder + attempt`，不依赖最终目标数量。界面普通新增与补全沿用种子，“随机”产生新种子，成功后将种子和生成关系一起保存。JSON 导出包含这些状态；只给出排序后的 HEX 而缺少生成关系，不构成相同历史输入。

### 4.2 v3 下一色：补过渡或探索邻近色系

空集合首先在 L `[0,1]`、C `[minChroma,maxChroma]`、h 全圆内进行带种子偏移的 Halton 抽样，C 按 `sqrt(Cmin² + u × (Cmax² − Cmin²))` 在环形面积上均匀映射，最多尝试 `16000` 点。首个能转成 sRGB HEX 且量化后彩度位于闭区间内的新色成为根节点；不按旧范围或文字对比挑选，也不为了得到易通过规则的根而重新挑色。单色操作可以成功且审计仍有冲突，界面必须明确显示这些冲突。继续生长前会完整审计已有集合，首色不符合文字、域或其他规则时直接停止。

后续每一步先估计当前范围的 OKLab 扇形柱体积 `V = ΔL × (C高² − C低²) × 色相弧角度 × π / 360`，其中 C 低端为 `max(域下界,minChroma)`，高端为 `min(域上界,maxChroma)`；没有交集时直接报告范围冲突。偏好步长取 `s = max(2.8, min(4.4, 70 × (V/25)^(1/3)), 1.6 × minDeltaE)`；固定使用 25 估计密度，不因本次是加一色还是补满而改变路径，也不意味着需要铺满整个体积。

随后从当前全部颜色构建完整 OKLab 距离的最小生成树，观察其中最长连接边。若它大于 `max(5.2, 1.6 × s, 3.2 × minDeltaE)`，本步选择补过渡，以这条边两端的 OKLCh 最短色相弧插值中点作为目标，L / C 线性插值，避免把 a/b 直线穿过灰心当作唯一过渡。否则，本步选择探索，偏好最近邻距离接近 s，兼顾三个邻近参考方向的占用量和色相偏离，使搜索同时考虑色相、明度与彩度变化。

每一步使用三轮各 `2048` 点的确定性 Halton 采样，复用既有转换、量化、文字和全对检查。每个候选必须在当前范围内，与所有现存颜色满足最小色差与底色最大对比，并满足文字对比和彩度上下界。v3 还筛掉离已有集合过远的候选：过渡时最近邻距离最多为 `max(6, 0.6 × 最长连接边)`，探索时最多为 `max(5.8, 1.8 × 偏好步长)`。这是工程上的局部连接筛选，不是用户硬规则或色彩标准，因此有限搜索可能放弃域内其他满足硬规则的颜色。

通过检查后，过渡评分偏好接近插值目标，同时考虑最近邻距离与参考彩度；探索评分偏好适度步长、相对较少覆盖的方向和参考彩度范围。方向覆盖按原始参考路径上的分布比例衡量，多色输入中少量端点色不代表要把三个方向强行均分；只有一个起点时才使用均衡的方向参考。

单主色不能表达整套色板的彩度分布，因此将它的 C 视为一个柔性范围的中心，而不是必须保持的半径。设起点彩度为 C₀，半宽 `w = min(0.018, s / 200)`，将 `[C₀ − w, C₀ + w]` 与生成域、硬彩度区间取交集，得到软容忍带 `[C低, C高]`。带内不因偏离 C₀ 扣分；带外代价为 `100 × (max(0, C低 − C, C − C高) + 0.25 × max(0, C低 − C))`，向灰偏离略多罚。带宽基于原始起点与固定范围，同一次生长中不随当前数量收缩，所以单步新增与补全仍共享同一序列。它不要求填满整个区间，也不强制颜色落在几条同心圆上。多主色继续沿参考路径使用原有双向彩度偏离代价。

这修正了早期 v3 单根评分的退化：当每次偏离唯一参考 C 都被线性扣分时，明度与色相会承担几乎全部变化，a/b 投影就收缩为固定半径圆弧。这是评分偏差，非单色起点的空间限制；多主色具有不同 C 时可以掩盖偏差，数量本身不保证消除它。复现输入、修正前后实码分布与两例对照见 [单主色径向实验](analysis/radial-growth.json)，摘要见 [验证记录](VALIDATION.md)。显式设定很窄的彩度域时仍可能形成窄弧，此时应遵守用户范围。

最终选择得分最低的候选，以它的最近已有颜色作为父节点，记录实际距离与本步策略，再进入下一步。参考方向、阈值、系数和预算都是可复核的工程参数，不保证任意输入都形成恰好两到三个色簇，也不保证有限搜索能补满 25 色。

所有多色结果在返回前再次审计实际 HEX。任何一步失败会返回诊断和可选的中间结果，工作台保持整个操作前的色板，既不应用半成品，也不悄悄修改固定颜色、降文字阈值或放宽色差要求。取消通过终止 Worker 完成。完整补全成功后才执行独立显示排序；新增和部分随机替换不会把未选槽位移走。

### 4.3 保留的 v2 候选池与近邻评分

本节描述独立的 `generatePalette` API，不是当前 v3 工作台的执行流程。种子确定候选采样序列；同样的主色、域、约束、目标数量、采样设置和种子在同一算法版本下产生相同结果。

生成流程如下：

1. 验证参数与固定锚点。目标数为 1–25；采样预算默认为 `16000`，可在 API 中设置 1–100000 的整数。固定集合不合格时立即返回，不改主色。
2. 对种子做逐个 UTF-16 字符的 FNV-1a 风格 32 位哈希，以确定性伪随机源生成三个偏移。Halton 序列使用基数 `2 / 3 / 5`，各维加偏移后对 1 取模。
3. L 和 h 按各自区间线性映射；C 使用 `sqrt(Cmin² + u × (Cmax² − Cmin²))`，使 a/b 平面的环形面积均匀，而非过度集中在低 C。
4. 每个候选转换为 HEX 后重算指标，拒绝出 sRGB、出域、超彩度、文字不足或与固定集合不兼容的颜色。去除重复色码，形成候选池。
5. 三轮仍在同一候选池中贪心补点，但评分由 maximin 改为近邻衔接：优先补足主色近邻路径中较少覆盖的位置，偏好适度单步距离、接近参考彩度，并兼顾 L / C / h 的变化方向。每加入一个点都更新最近距离，兼容性检查仍使用全部硬约束。第二、三轮只在软评分上加入种子确定的微扰。
6. 按完成数量优先、参考路径偏离代价其次选取结果，不再以更大的全对最小距离作为次优目标。最后再次完整审计实际 HEX。

参考路径由主色的完整 OKLab 近邻最小生成树构建，边上以 OKLCh 最短色相弧和线性 L、C 插入参考点，避免直接穿过 a/b 灰心导致彩度塌陷。中性主色不以不稳定的色相引导路径。路径节点与候选的距离只用于软评分：不会排除用户域内本来可行的候选，也没有额外的隐藏色相或彩度硬边界。单主色仍有 L、h、C 三个探索方向，但不能从单一输入推断未表达的多色系意图。

步长、路径采样密度和评分权重是项目工程参数，并非 OKLab 或 WCAG 标准给出的审美公式。v2 多主色偏好步长约为 ΔE `4`，单主色为 `2`，同时不低于用户色差下限的 `1.25` 倍；它是软目标，无法保证任意输入都有此步长的可行解。原例的最近邻与 MST 分布用作回归证据，不作逐点复刻目标。

彩度偏离按双向代价计算：`100 × (abs(C − C参考) + 0.25 × max(0, C参考 − C))`。这里略增加向灰侧的代价，但高于参考彩度也受罚。只惩罚向灰会使环面积采样与评分叠加后系统性偏向鲜艳，因此不能把“保留彩度”实现成“彩度越高越好”。

这不是连续域的全局最优求解。微扰可增加尝试方向，但无法消除有限候选池和贪心策略的局限。

- `success`：完整数量与全套审计同时通过。
- `partial`：有限搜索找到一部分可用补点，仍未达到目标。
- `failure`：输入、固定集合或搜索结果无法形成可用完成方案；具体原因在 `diagnostics` 和 `validation.issues` 中。

v2 API 的局部结果可以附带 `partialColors` 供诊断，搜索不会悄悄降低 `minDeltaE`、放宽对比范围或改变锚点。历史工作台只应用完整 `success`；当前工作台的结果应用与首色例外见第 4.1–4.2 节。

必须区分两种结论：固定锚点中已存在一对小于要求的色差，且要求保留它们时，该固定集合确实不能满足当前约束；而有限候选搜索未找到 25 色，只能说明本次搜索不足，不能证明连续域里不存在可行解。窄域、严格距离下界和固定底色跨度也可能让贪心过程较早用尽候选。

## 5. 局部修复、候选检查与色彩探索

本节的局部重生成描述保留的 v2 底层 `regenerateSelected` API 与历史实验，不是当前工作台“随机”按钮的实现。当前随机替换使用第 4.1 节的统一逐色流程；也可删除选中颜色后再补全。

局部重生成先把未选颜色作为固定集合审计，与主色列表是否为空无关。全选时固定集合可以为空，仍保留目标数、有效域和全部硬约束。原完整色板默认作为软评分参考，避免全选后丢失原风格；它不会被直接当成候选池。若固定集合有效，新色必须与每一个固定颜色及已经产生的新色满足同样边界，且排除原色板中的所有 HEX，确保替换为新色。最终结果恢复到原槽位，不额外排序；成功时未选 HEX 和位置保持原值。API 的 `indices` 使用从 0 开始的下标。

编辑器使用不同的增量检查语义：`checkCandidate(candidate, existing, constraints, domain)` 的 `hardAllowed` 只判断候选自身及涉及候选的颜色对，避免其他已知冲突阻止逐个修复。它同时返回整套 `validation`，因此允许出现 `hardAllowed = true` 而 `validation.valid = false`。生成器则先审计整个固定集合，不能利用增量语义绕过原有冲突。

批量绘图时，`createCandidateChecker(existing, constraints, domain)` 快照固定集合的指标与审计；每个候选只追加自身和 n 个相关颜色对，工作量为 O(n)，仍返回与完整审计相同的指标和问题语义。颜色、参数或域变化后必须重新创建检查器。

色彩地图是当前 L 的 a/b 平面切片：向右为 h = 0°，逆时针改变色相，距中心越远 C 越大。可见范围根据当前 Display P3 截面自适应，不使用固定彩度半径作为风格限制。缩放以当前预览点或编辑色为中心，展开提供更大的操作区域；修改 L 会重算整个截面。

地图区分四种信息：

1. **sRGB 边界**：将 OKLab 点变换到线性 sRGB，检查各通道是否在 `[0,1]` 内。边界按色相方向进行二分求解，并以连续路径叠加在高分辨率图像上。
2. **Display P3 参考边界**：经 D65 XYZ 变换到线性 Display P3，再使用同样的通道范围检查。这里采用 Display P3 的白点和矩阵，不能替换成 DCI-P3。参考环带以灰色展示，不用裁剪后的 sRGB 假扮 P3 色彩；最终输出始终为 sRGB。[W3C 色彩转换参考](https://www.w3.org/TR/css-color-4/#color-conversion-code)
3. **生成范围**：按 L、C、h 区间画独立的边界。当前 L 不在生成域内时没有该域的截面，界面明确提示。完整色相圈没有人为的径向接缝，跨零圆弧按真实角度绘制。
4. **硬约束提示**：斜线为稀疏采样得到的诊断示意，与设备边界和生成域分别显示。它不能代替逐个实码审计；悬停卡会对实际量化 HEX 计算 L/C/h、文字对比和具体失败原因。

颜色选择和生成可行性分开处理。地图允许应用任意可转换为 sRGB HEX 的点，不因出生成域或违反当前对比、彩度、距离条件而阻断探索；这些条件持续显示诊断，并在生成前完整检查。超出 sRGB 的点没有可用 HEX，不能应用。图中不再有独立的 `C = 0.1` 点选门槛。

拖动时只更新预览，松开时应用；键盘也可预览后确认。HEX 是唯一颜色编码输入，L/C/h 控件负责感知维度的微调。六个方向候选分别以 `±0.04` 调明度、`±0.015` 调彩度、`±15°` 调色相，解释变化方向，超出 sRGB 时禁用。候选本身不保证满足全套规则。八位量化可能让未修改的坐标发生微小变化，指标始终从实际色码重算。

## 6. 排序的目标与边界

排序先利用最大的圆形色相空隙选取切口。覆盖弧小于 `35°` 时分 1 组，小于 `85°` 时分 2 组，其余分 3 组；以内部最大的色相间隙确定组界。每组从最暗的色点起步，每一步选 OKLab 距离最近的剩余点。连接后续组时，比较正向与反向路径端点，选择较小的接续跳跃。

这是一种方便浏览与微调的启发式排列，目标是减少同组相邻步长和组间跳跃。它不求解全局旅行商最优，也不保证明度整体单调。排序仅置换现有色码，因此全对最小距离、最极端底色对比和文字对比都保持不变。

工作台在每次完整生成成功后调用该排序，不修改生成器候选池或选点评分。手动新增、编辑或删除后，根据当前序列是否已等于排序结果显示“排序”或灰色“已排序”；选中集合和编辑对象随置换映射，避免把旧下标错误地指向另一种颜色。

### 7.1 参考色板证明约束集合非空

`src/presets.ts` 中的 `WATERFOREST_COLORS` 是原始 25 色参考表，不参与生成器候选构造。`DEFAULT_DOMAIN` 只通过以下 5 个锚点推导：

这份历史实验使用的固定域与约束为：

| --- | ---: | ---: |

八位量化不会使这个解只剩零体积的孤立点：每个参考 RGB 码的通道中心附近都有正宽度的舍入区间。参考点严格在域内、彩度非零，色彩转换在这些点附近连续且局部可逆，因此量化区间与允许的 OKLCh 体积有正体积交集；交集内的浮点点会转换成相同 HEX，接受相同审计。

这说明通用色彩模型为这些颜色提供了采样邻域。若候选池只包含这些目标量化区间产生的色码，现有兼容性检查和贪心补点可选择同一集合。**但本版种子被映射为有限的 32 位状态，采样预算也有限；上述几何论证不证明必然存在一个种子精确复现原始 25 色，更不承诺任意种子都能复现。**

### 7.3 复现固定实验输入

界面可从只读示例逐个取主色，也可显式“使用主色”加载该示例输入；后者保留用户文字设置，种子仍由工作台指定。相同输入在同一算法版本内可复现；v2 改变补点评分，因此不会返回 v1 的同一组颜色。当前 v3 工作台另有逐色生长流程，以下调用用于复核保留的 v2 引擎，不能用来代表当前按钮的执行结果。

复核这组固定输入在保留的 v2 引擎下的结果时，显式使用 `DEFAULT_DOMAIN` 和 `DEFAULT_CONSTRAINTS` 调用引擎：

```ts
import { generatePalette, validatePalette } from './src/generator';
import {
```

## 8. 研究取舍

本版选 OKLab 欧氏距离与 WCAG 比值，分别处理色彩密度和文字 / 背景边界。CIEDE2000 使用 CIELAB 输入，不与当前距离数值混用。APCA 仍涉及 beta 状态、字体参数和专用许可，本版没有引入其算法或依赖。来源、版本与许可记录见 [SOURCES.md](SOURCES.md)。
